# 技能系统神系重做设计

## 概述

游戏将用“神系技能池”替换当前“武器绑定技能成长”的模型。玩家运行流程中不再有武器、武器分支、武器绑定起始技能和武器进化。神系单独定义在 `data/gods.json`；玩家技能定义在 `data/skills.json`，并通过 `god_id` 关联所属神系。

第一批实现会定义全部六个神系，并实现火之神的 60 个技能。其余五个神系第一版只提供神系定义，技能池后续分批接入。

## 目标

- 在 `data/gods.json` 中独立定义六个神系：火焰、雷霆、寒霜、诅咒、神圣、混沌。
- 在 `data/skills.json` 中实现火焰 60 个文档技能。
- 确保每个已实现火焰技能都能按照当前稀有度权重出现在升级池中。
- 确保每个已实现火焰技能在选择后都对本局战斗产生真实效果。
- 从主流程中移除武器概念，而不是用兼容字段把武器藏起来。
- 所有技能视觉效果使用基于 `GPUParticles2D` 的简单 2D 粒子。
- 保持伤害、状态、暴击、目标选择、减伤等结果继续走现有战斗计算链路。
- 将敌人当前数字血量展示替换为可视化血条，扣血时血条变化带缓动反馈。

## 非目标

- 本批不实现其余五个神系的技能。
- 不保留武器分支或武器进化行为。
- 第一版不为复杂技能制作完整专属演出系统。
- 除非基础可用性必须，否则不新增复杂技能状态 UI。
- 不保留“能抽到但对战斗无影响”的技能卡。

## 用户确认的实现标准

每个火焰技能都必须满足：

1. 出现在升级池中，稀有度概率与当前游戏设置对齐：普通 60、稀有 28、史诗 10、传说 2。
2. 选择后必须有具体对局效果。有效效果包括伤害、状态附着、被动触发、冷却变化、范围变化、弹体数量变化、护盾、反击、复活、延迟伤害，或其他符合技能描述的战斗行为。
3. 禁止只把技能卡接入升级池。只要技能可选，就必须影响本局对战。
4. 技能视觉使用 `GPUParticles2D` 实现的简单 2D 粒子。
5. 复杂描述可以第一版做“简化但真实生效”的机制。例如 `太阳熔炉` 可以周期性强化下一次火系技能的伤害、范围或数量，并播放短暂金红锻造粒子；不要求第一版实现持续存在的熔炉实体、专属 UI 或完整动画系统。
6. 每个技能都必须声明一个运行族。若现有运行族无法表达技能描述，必须补充新的运行族、运行规则和文档备注，不能把技能强行塞进不匹配的族。
7. 角色初始技能的第一版视觉可以使用简单矩形或圆形粒子/形状代替，不需要专属美术资源。
8. `mars_spark_missile` 是火系第一个可学习技能及其粒子表现，不是人物初始攻击。当前默认初始攻击按 `fireball` 迁移，且不再通过武器解析。
9. 火系技能实现后，当前 dev tools 必须增加调试入口，可在不进入主流程升级流程的情况下验证“选择技能卡 -> 获得技能 -> 施放/触发技能 -> 敌人受伤、状态附着、粒子和伤害跳字反馈”的完整链路。

## 数据设计

### `data/gods.json`

文件顶层包含 `gods` 数组。每个神系定义使用稳定英文 id 和中文显示文本。

必需字段：

- `id`：稳定 id，例如 `fire`。
- `display_name`：中文名，例如 `火焰`。
- `title`：文档标题式名称，例如 `火之神`。
- `description`：简短玩法定位。
- `tags`：神系级标签，用于技能权重和协同。
- `color`：用于通用粒子和 UI 强调色的 RGBA 颜色。
- `implemented`：当前批次是否已有可玩的技能池。

第一批神系：

- `fire`：已实现，60 个技能。
- `thunder`：仅神系定义。
- `frost`：仅神系定义。
- `curse`：仅神系定义。
- `holy`：仅神系定义。
- `chaos`：仅神系定义。

### `data/skills.json`

文件顶层包含 `skills` 数组。如实现需要，也可以包含可选的 `skill_upgrade_cards` 生成元数据。火焰技能必须是具体运行时定义，不能是占位记录。

每个技能必需字段：

- `id`：稳定 snake_case id，尽量按含义生成，而不是拼音。
- `display_name`：文档中的中文技能名。
- `god_id`：第一批火焰技能全部为 `fire`。
- `rarity`：内部稀有度 key：`common`、`rare`、`epic`、`legendary`。
- `source_rarity`：原始中文稀有度：`普通`、`稀有`、`史诗`、`传说`。
- `description`：文档技能效果，可做少量清晰化编辑。
- `vfx_description`：文档特效描述。
- `build_hint`：文档后续构筑说明。
- `category`：`active` 或 `passive`。
- `runtime_family`：技能所属运行族，例如 `projectile`、`cone_area`、`stack_mark`。如果新增运行族，必须同步记录运行族说明和适用技能。
- `tags`：标准化标签，例如 `fire`、`projectile`、`burn`、`shield`、`retaliation`、`boss`、`cooldown`、`summon`、`execute`。
- `max_level`：技能等级上限数据。第一版不把主动技能数量或等级硬写死为 5；后续可以接入更科学的限制规则。
- `base`：组件和 action 需要的运行数值。
- `components`：冷却、目标选择、持续环绕或被动触发组件。
- `events`：施放、命中、击杀、玩家受击、状态结束等事件触发的 action。
- `particle`：`GPUParticles2D` 视觉 profile 引用或内联粒子参数。

可选字段：

- `runtime_rules`：需要自定义代码支持的第一版规则数据。
- `offer_rules`：可用性和权重调整。
- `skill_modifiers`：拥有该技能时提供的被动 modifier。

## 稀有度映射

源表稀有度映射到运行时 key：

- `普通` -> `common`
- `稀有` -> `rare`
- `史诗` -> `epic`
- `传说` -> `legendary`

第一批火焰技能数量：

- 24 个普通技能。
- 18 个稀有技能。
- 12 个史诗技能。
- 6 个传说技能。

升级池沿用当前稀有度权重，除非后续明确要求神系专属调权。

## 运行时架构

### 数据加载

`DataManager` 成为以下数据的主要加载入口：

- `data/gods.json`
- `data/skills.json`
- 敌人、波次、状态、遗物、协同、地图、升级、角色等现有非武器数据

`DataManager` 不再从 `primary_attack.json` 或 `learnable_skills.json` 索引玩家技能。`GameData` 的 fallback 函数也保持同样行为。

### 开局配置

`RunLoadout` 只保存角色数据。不再保存 `weapon_id`、`weapon_data` 或 `weapon_definition`。

`CharacterLoadoutService` 只校验角色。角色定义不再需要 `allowed_weapon_ids`。

`PlayerController.reset_for_loadout()` 初始化角色、清空本局技能状态、应用角色属性和 trait，并授予当前初始技能。初始技能作为“开局机制”保留，但不再通过武器解析。实现时可以把它放在角色字段、运行配置字段或明确的默认起始技能 id 中，但不能依赖武器定义。

### 从主流程移除的系统

以下概念从当前可玩运行流程中移除：

- 武器选择。
- 武器装备校验。
- 武器视觉刷新。
- 武器绑定起始技能。
- 武器分支选择。
- 武器分支等级卡。
- 武器进化卡。
- 当前武器技能判断。
- 武器专属 debug full matrix 流程。

如果直接删除旧文件会造成不必要的 Godot 资源 churn，第一版可以让旧文件暂时留在磁盘上；但主流程和验证路径都不能再依赖它们。

### 升级池

升级池改为技能优先：

- 如果技能未拥有，且主动技能槽未满，生成学习技能选项。
- 如果技能已拥有且支持升级，生成升级技能选项。
- 现有非技能生存和 meta 升级可以保留，但不能要求武器标签。
- 现有武器标签升级需要删除、禁用或迁移为通用技能标签。
- 永远不再生成分支和进化选项。
- 配置的初始技能在开局已经拥有，不再作为重复学习卡出现。

### 技能执行

现有系统仍是核心执行路径：

- `SkillManager` 持有主动和被动技能。
- `SkillExecutor` tick 主动技能。
- `SkillComponentRunner` 处理冷却和目标选择。
- `SkillEventBus` 分发技能事件。
- `SkillActionExecutor` 生成投射物、区域、环绕物、陷阱、状态、治疗、modifier 和伤害。
- 现有伤害服务负责最终伤害计算。

实现时可以新增一个聚焦的火焰规则层，用于当前通用 action 表达不了的行为。该层必须由 `runtime_rules` 数据驱动，不能靠卡牌文本硬编码。

## 视觉效果

第一批所有技能视觉都使用简单粒子效果。

实现时应新增可复用粒子路径，例如：

- 基于 `GPUParticles2D` 的通用 `skill_particle_effect.tscn`；或
- 根据数据创建 `GPUParticles2D` 节点的 `SkillParticleFactory`。

粒子 profile 应支持：

- 主色和副色。
- 生命周期。
- 发射形状。
- 粒子数量。
- 初速度。
- 扩散角。
- 缩放。
- 在可行范围内支持径向、扇形、爆发、拖尾、环绕、命中等模式。
- 角色初始技能允许使用简单圆形或矩形粒子/形状作为第一版表现。

目标是提供清晰战斗反馈，而不是制作专属动画。火焰投射物可以使用橙色小拖尾；火焰脉冲可以使用径向爆发；凤凰复活可以使用更大的金红爆发。

## 火焰技能实现规则

60 个火焰技能都必须实现为“简化但真实生效”的机制。示例：

- 投射物技能使用 `spawn_projectile` 或 `spawn_projectiles_at_targets`，造成火焰伤害并显示火焰粒子。
- 扇形或脉冲技能使用带扇形或半径参数的 `spawn_area`。
- 环绕技能使用环绕物或周期性径向区域。
- 标记技能施加状态层数，并通过运行时规则消耗层数。
- 击杀触发技能订阅击杀事件，生成后续伤害或缩短冷却。
- 反击技能响应玩家受击，并带触发冷却。
- 护盾和护甲技能提供护盾、减伤或临时 modifier。
- Boss 和高生命技能使用生命比例、精英或 Boss 条件。
- 传说技能提供广泛但具体的效果，例如复活、周期性强化技能或按火焰技能数量缩放。

任何缺少运行时影响的火焰技能都不能标记为已实现。

## 错误处理

- 缺少 `god_id` 或引用未知神系时，验证失败。
- 缺少粒子 profile 时，回退到简单火焰爆发并记录 warning。
- 不支持的 action 或 runtime rule 必须在验证阶段失败，而不是运行时静默生成无效卡。
- 稀有度非法的技能从池中排除，并由验证报告。
- 主动技能槽满时，不再提供学习技能卡。

## 测试与验证

验证脚本应覆盖：

- `gods.json` 正好有六个唯一神系。
- `skills.json` 第一批正好包含 60 个火焰技能。
- 每个火焰技能都引用 `god_id: "fire"`。
- 每个火焰技能都有合法稀有度、显示名、描述、特效描述、构筑提示、分类、标签和粒子数据。
- 每个可选火焰技能都有可执行 components/events、被动 modifiers 或受支持 runtime rules。
- 每个火焰技能都有合法 `runtime_family`；新增运行族必须有文档说明和运行规则。
- 升级池能用现有稀有度权重生成学习技能卡。
- 选择火焰技能后，会加入 `SkillManager` 或应用其被动运行时行为。
- 自动化 smoke 不只验证数据，还要模拟选择技能卡后攻击一次敌人，观察/断言弹道或粒子特效、状态附着、伤害跳字，以及伤害结果符合现有伤害公式链路。
- 每类代表性火焰机制至少验证：造成伤害、施加状态、修改冷却、击杀触发、受击触发、显示粒子。
- 玩家 loadout 不再需要武器。
- 不再生成分支和进化选项。
- 旧武器数据不会被加载进玩家技能池。
- 敌人使用可视化血条展示当前生命；扣血时即时血量和缓动血量都能正确更新。

手动 Godot smoke 检查应包括：

- 只选择角色即可开始运行。
- 确认当前初始技能在不选择、不加载武器的情况下被授予。
- 升级并选择一个火焰技能。
- 确认粒子出现。
- 确认敌人通过正常伤害系统扣血。
- 确认至少一个状态型火焰技能能施加或消耗状态。
- 确认没有武器、分支或进化 UI 出现。
- 确认敌人扣血时血条有平滑缓动，伤害跳字仍正常显示。

## 已确认补充

- 第一版不再保留“主动技能槽上限 5”作为硬限制，后续会接入更科学的限制设置。
- 技能等级和重复成长规则不在第一版写死为 5 级。
