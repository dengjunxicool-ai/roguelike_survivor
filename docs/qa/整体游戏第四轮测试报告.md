## R4 01 主存档缺失导致已持久化的待补存记录丢失

**复现条件与步骤：**

1. 在隔离目录建立合法主档，余额 100、总局数 7、总击杀 111；调用公开 `reset_progress` 建立 UUID epoch。
2. 创建 `user://save.cfg.tmp` 同名目录，使主档提交失败。启动生产 App，击杀实际掉落 35 灵魂石的骷髅队长，并触发一局 301 秒、42 杀的胜利结算。实际死亡流程及结算提交入口参与测试，终局时间和击杀为受控输入。
3. 确认 `pending_rewards.cfg` 已保存两项待补存记录，然后仅将主档移为 `original-save.cfg`，保留原字节和 journal。
4. 调用 `retry_pending`，或者在主档仍缺失时重新启动进程。
5. 恢复原主档字节，解除临时文件写入故障，再重试补存。

**实际：** 主档缺失时 epoch 被读取为 `legacy`，UUID epoch 的两项记录直接删除并写回空 journal。原主档恢复后余额仍 **100**、总局数仍 **7**、总击杀仍 **111**，35 个灵魂石及这局进度不再补发。期望应最终达到 **135 / 8 / 153**，重复重试不重复计数。

**覆盖对照：** 同进程移走恢复、跨真实进程重启、删除主档后恢复保留字节都成立。普通新用户无主档且无 journal 正常首存，35 魂与一局成功保存。合法 `legacy` 旧档也有相关边界：主档缺失并恢复可写后，补存服务以空基档写出余额 35、局数 1、击杀 42 并清空 journal；再恢复旧档则回到 100 / 7 / 111，无法补发。

**可达性限制：** 外部移动、删除或备份恢复主档是本项必要条件，未发现纯菜单操作造成文件消失。当前 UI 没有 `reset_progress` 调用，普通首次保存仍为 `legacy`；UUID 清队列分支对应公开 reset API 建立的存档。legacy 对照覆盖当前普通存档格式，但仍需要外部文件恢复。不能据此声称正常对局必然丢档。

**根因位置：** [主档读取许可](../../scripts/game/save_manager.gd:62)把文件不存在视为新用户可写；[epoch 查询](../../scripts/game/save_manager.gd:40)于是返回 `legacy`；[启动清理](../../scripts/game/pending_save_service.gd:87)和[失败重试](../../scripts/game/pending_save_service.gd:71)据此丢弃不同 epoch 的记录。缺失旧主档与主动重置进度未作区分。

**修复方向与验收：** 存在合法待补存 journal 时，主档缺失应进入恢复待定状态，保留记录并提示故障；只有明确成功的新 epoch 重置才能淘汰旧记录。兼容真正新用户首次保存。复验 UUID / legacy、移走 / 删除 / 重启、原档恢复、主动 reset 和重复重试，恢复后只补发一次。

**证据：** [根测试独立复验](E:/codex/game-qa-round4-20261011/persistence/root-missing/missing-local.json)、[对应日志](E:/codex/game-qa-round4-20261011/persistence/root-missing/result.log)、[跨进程恢复](E:/codex/game-qa-round4-20261011/persistence/missing-restart-c/missing-recover.json)、[legacy 对照](E:/codex/game-qa-round4-20261011/persistence/legacy-missing-a/legacy-missing-writable.json)。根复验日志另出现一次 R4 05 错误；资源遗失由存档和 journal 观测独立确认。

## R4 02 待补存文件短暂不可读后恢复状态被锁定

**复现步骤：**

1. 合法主档余额 100。阻止主档提交，击杀骷髅队长，使 35 魂奖励保存在合法 journal，退出该测试进程。
2. 通过 Windows `FileShare.None` 真实独占锁占用 journal，启动下一进程。首次读取失败为 `ERR_FILE_CANT_OPEN=12`。
3. 解除独占锁，确认相同 journal 原字节仍在，新的 `ConfigFile.load` 已返回 OK。此时主档写入仍受阻。
4. 执行重试，再击杀一个骷髅队长，调用退出准备；最后恢复主档写入，并再次重启作对照。

**实际：** 解锁后 `_journal_readable` 仍为 false，旧待发队列仍为空，故障提示为空。新增 35 魂只能留在内存；已可读写的 journal 不能接收新增奖励，退出准备返回 false。恢复主档写入只补发新奖励，钱包 **100 → 135**；再一次重启才恢复旧 35 魂至 **170**。首次读取故障会使恢复功能在整个进程内失效；本次受控退出没有造成最终重复发奖或永久丢失。

**预期：** 文件恢复可读后重新加载并合并旧记录，保持 receipt 幂等；恢复原奖励、继续持久化新增失败奖励，并显示正确状态。

**根因位置：** [初始化读取](../../scripts/game/pending_save_service.gd:14)仅发生一次；[定时重试](../../scripts/game/pending_save_service.gd:29)不包含首次读取失败且队列为空的情形；[journal 保存](../../scripts/game/pending_save_service.gd:99)在 `_journal_readable=false` 时永久短路，没有重新读取路径。

**修复方向与验收：** 对暂时无法读取的 journal 保留故障状态并重读，恢复成功后安全合并内存新增记录，避免覆盖旧字节。验收真实短时独占锁、正常解锁、持续占用、损坏文件保护、新增内存奖励合并和跨进程幂等；原 35 与新 35 均最终只发放一次。

**证据：** [根测试独立解锁观测](E:/codex/game-qa-round4-20261011/persistence/root-journal-lock/journal-lock-recover.json)、[下一次重启观测](E:/codex/game-qa-round4-20261011/persistence/root-journal-lock/journal-replay.json)、[无脚本或引擎错误的阶段结果](E:/codex/game-qa-round4-20261011/persistence/root-journal-lock/journal-lock-recover-result.json)。`journal-lock-b`、`journal-lock-c` 和根复验均成立。

## R4 04 延迟补存使最近一局摘要回退

**复现步骤：**

1. 旧主档累计 7 局、111 杀。使主档提交失败，经生产结果入口留下 A 局结算，受控摘要为 301 秒、42 杀。
2. 正常返回菜单再启动 B 局，恢复可写，在下一次补存重试前通过生产入口提交 B 局，摘要为 22 秒、3 杀。
3. 确认最近摘要是 B，再触发 A 的补存。

**实际：** B 成功时最近摘要为 **3 杀 / 22 秒**；A 补存后回退为 **42 杀 / 301 秒**。累计进度正确为 **9 局 / 156 杀**。同一顺序在三个 fresh 目录复现。

**预期与范围：** 若 `last_run_summary` 表示最近结束的一局，历史补存应累计进度但不能覆盖较新局的摘要。目前 [getter](../../scripts/game/save_manager.gd:229)没有生产 UI 调用者，因此按 P3 持久化 API 语义问题记录；未发现当前结果页显示、奖励推荐或累计进度因此错误。若产品约定其表示“最后写入的记录”，应明确改名或说明该语义。

**根因位置：** [结果提交](../../scripts/game/run_progression_service.gd:31)无条件写 `last_run_summary`，记录中没有跨重启可比较的结束顺序；补存服务提交旧记录时使用相同入口。

**修复方向与验收：** 记录结束顺序或持久化序号，只让较新结算更新最近摘要，保留旧结算计数及解锁的幂等提交。验证 A 失败、B 成功、A 恢复、重复恢复及跨重启；最近摘要保持 B，累计两局只计一次。

**证据：** [摘要先后顺序观测](E:/codex/game-qa-round4-20261011/persistence/summary-order-c/summary-order.json)、[运行日志](E:/codex/game-qa-round4-20261011/persistence/summary-order-c/result.log)。终局数据为受控输入，此用例不证明 22 秒自然通关。

## R4 05 补存状态通知读取不存在的 receipt 产生错误

**复现步骤：**

1. 使用合法 `legacy` 旧档，不含 `pending_receipts` section；阻止主档提交并产生真实结果页及一项待补存结算。
2. 保持写入故障，在没有任何文件写入的观察窗口，仅连续三次发出生产 `PendingSaves.status_changed` 通知。
3. 恢复主档写入，重试并检查结果页及局数。

**实际：** 三次通知分别产生一个 `Couldn't find the given section "pending_receipts" and key ... and no default was given` 引擎错误，共 **3 次**。调用栈为 `SaveManager.load_value:87 → UIManager._on_persistence_status_changed:257`。错误来自缺失键读取，已与预期临时文件写失败日志隔离。生产失败重试也会发出该通知；根 R4 01 复验同时记录一次同类错误。

结果页仍保持胜利、未保存状态和待补存提示；恢复后总局数 7 → 8，记录标志正常更新。此问题未造成额外资源损失或崩溃，按 P3 处理。

**根因位置：** [状态通知](../../scripts/ui/ui_manager.gd:257)以 null 作为缺失 receipt 的默认值，传到 [配置读取](../../scripts/game/save_manager.gd:87)后，Godot 将其视为未提供默认值并记录错误。

**修复方向与验收：** 查询前检查键是否存在，或使用不会触发缺失错误的明确默认值；保留“receipt 为 Dictionary 才视为结算成功”的行为。合法旧档缺键、当前档无这局 receipt、持续失败和恢复均应无额外读取错误，且失败结算不能提前标为保存成功。

**证据：** [独立三次非写入通知日志](E:/codex/game-qa-round4-20261011/persistence/receipt-errors-b/result.log)、[错误计数](E:/codex/game-qa-round4-20261011/persistence/receipt-errors-b/result.json)、[界面状态及恢复观测](E:/codex/game-qa-round4-20261011/persistence/receipt-errors-b/receipt-errors.json)。Godot 脚本退出 0，但隔离验证器因捕获 3 个引擎错误返回失败；该结果作为缺陷证据，不计入通过用例。

## 待设计确认和未覆盖范围
