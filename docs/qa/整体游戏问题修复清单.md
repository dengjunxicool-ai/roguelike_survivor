## QA01 残留伤害区域访问已释放施法者

**影响：** 持续伤害事件触发 `SCRIPT ERROR: Trying to cast a freed object`，事件上下文构造中断。16 次自动战斗中有 5 次出现，共 19 条；未观察到整个进程崩溃。

**复现步骤：**

1. 让敌人施放可独立存续的持续伤害区域。
2. 击杀并释放施法者，保留其已激活的区域。
3. 让区域继续命中目标并发送 `area_tick`。
4. 检查日志。最小复现也可先释放 context 中的 caster，再调用真实事件总线发送 `area_tick`。

**预期：** 来源节点死亡后，合法残留区域仍按规则运行，事件入口安全处理失效引用。

**实际：** `SkillEventContext.from_context` 在第 30 行强转失效 caster 时报错。

**代码位置与原因：**

- [skill_event_context.gd](../../scripts/skills/skill_event_context.gd:30)：在对象有效性清理前把 caster 强转为 Node。
- [skill_event_bus.gd](../../scripts/skills/skill_event_bus.gd:120)：`purge_invalid_references` 在后续派发阶段执行，晚于上下文构造。
- [area_effect.gd](../../scripts/combat/area_effect.gd:1363)：残留区域事件携带施法者引用。

**修复建议：** 在首次类型转换和节点访问之前清理失效引用，检查同一入口的 target、owner、manager 等引用；保留伤害来源的数值快照，不以简单销毁全部残留区域替代其存续规则。

**验收标准：**

- [x] 最小复现无脚本或引擎错误。
- [x] 真实敌方区域激活后释放施法者，继续跳伤不报错，伤害与来源归因符合规则。
- [x] 有效施法者事件仍正常派发，不重复伤害或重复触发。
- [x] 原 5 个报错组合使用相同控制输入复测，日志不再出现该错误。

**证据：** [最小复现脚本](E:/codex/game-qa-20261010/repro_freed_caster.gd)、[错误日志](E:/codex/game-qa-20261010/freed-caster-01/result.log)、[16 局错误汇总](E:/codex/game-qa-20261010/combat-16/error-summary.json)。

## QA02 技能替换窗口被遮挡并发生点击穿透

**影响：** 玩家无法正常操作替换目标，点击可能消费原升级选择、恢复战斗并遗留替换窗口。

**复现步骤：**

1. 在本局普通主动替换次数尚未使用时，填满 5 个普通主动槽。
2. 打开升级选择，选择一张符合学习条件、尚未拥有的新普通主动技能。
3. 诊断脚本使用“圣盾卫士”候选进入普通升级入口，创建替换事务。
4. 检查窗口显示，并在替换目标按钮位置发送实际鼠标按下和抬起事件。

**预期：** 替换窗口位于选卡页面上方，输入被该模态独占；确认前保持暂停，取消返回原选择。

**实际：** 替换层为 120，UIManager 层为 200，原卡片覆盖替换窗口并接收点击。点击后 `state=RUNNING`、`paused=false`、升级待办为 0；替换窗口仍存在，`ordinary_replacement_used=false`。

**代码位置与原因：** [skill_replacement_view.gd](../../scripts/ui/skill_replacement_view.gd:5) 与 [ui_manager.gd](../../scripts/ui/ui_manager.gd:117) 的 CanvasLayer 层级逆序，模态显示与输入生命周期没有形成一致约束。

**修复建议：** 统一模态层级和输入阻挡；替换期间禁止底层卡片操作。同步维护暂停、待办队列、替换事务和窗口销毁状态。

**验收标准：**

- [x] 在 1280×720、960×540 和 800×600 下，替换内容、目标和取消均可正常操作。
- [x] 使用鼠标事件点击目标，不通过 `pressed.emit()` 代替交互验收；底层卡片不响应。
- [x] 确认后仅替换选定槽位，保持新技能品质，每局次数只消耗一次，无窗口残留。
- [x] 取消后返回同一次选择，不消耗奖励或替换次数；暂停状态正确。

**证据：** [遮挡截图](E:/codex/game-qa-20261010/render-01/replacement-overlay.png)、[观测 JSON](E:/codex/game-qa-20261010/probe-03/observations.json) 的 `replacement_overlay`。

## QA03 满主动槽时奖励技能被消耗却未学习

**影响：** 精英奖励被吞掉，玩家没有得到技能，也没有机会替换已有技能。

**复现步骤：**

1. 玩家 Lv12，普通主动槽 5/5，本局替换机会尚未使用。
2. 奖励池 RNG 设为 0，内部升级池 RNG 设为 1000。
3. 生成真实精英奖励，得到史诗“圣盾卫士”，技能 ID 为 `holy_summon_shield_guardian`。
4. 通过奖励选择回调领取该卡，检查技能、奖励队列和替换窗口。

**预期：** 按普通主动槽规则进入替换事务；无法应用时保留奖励并给出明确反馈。

**实际：** `learned=false`、`pending_rewards=[]`、`replacement_view_count=0`，状态回到 RUNNING。

**代码位置与原因：**

- [ui_command_dispatcher.gd](../../scripts/ui/ui_command_dispatcher.gd:40)：`reward_kind` 分支跳过普通学习分支的替换检查，未校验应用成功就返回 `consumed_reward=true`。
- [run_choice_modal_controller.gd](../../scripts/ui/modals/run_choice_modal_controller.gd:863)：根据返回值消费奖励。

**修复建议：** 让奖励与普通升级共用学习结果和替换事务；区分“已成功应用”“等待替换”“应用失败”，仅成功提交后消费奖励。与 QA02 一起联调。

**验收标准：**

- [x] 满槽且可替换时进入替换界面，不提前消费奖励。
- [x] 确认替换后新技能学会、品质正确、槽位数量正确，奖励只消费一次。
- [x] 取消、替换次数已耗尽或候选失效时，不吞奖励；交互符合既定规则。
- [ ] 未满槽和已拥有技能升级仍正常处理，无重复学习或重复领取。

**证据：** [观测 JSON](E:/codex/game-qa-20261010/probe-03/observations.json) 的 `generated_reward_replacement` 与 `reward_replacement`。

## QA04 部分 Boss 祝福引用不存在的升级

**影响：** 玩家消耗 Boss 前祝福选择，却没有得到所述增益。

**复现步骤：**

1. 生成 Boss 前祝福，选择“强敌压制”或“状态共鸣”。
2. 查询候选引用的 `boss_damage`，记录选择前后的 ModifierStore 来源。
3. 检查派发结果及实际修正。“Boss 补强”保底卡使用相同引用。

**预期：** 卡片所述 Boss 输出或 DOT 与反应补强生效，选择成功后消费。

**实际：** GameData 和升级仓库查询均为空，ModifierStore 不变，但返回已处理、已消费。

**代码位置与原因：** [run_reward_pool.gd](../../scripts/upgrades/run_reward_pool.gd:61) 的第 61、64、140 行引用缺失升级；派发缺少失败结果处理。现有内容校验没有覆盖代码内生成的奖励引用。

**修复建议：** 为三张卡配置合法且与描述相符的效果，不能只以同一个无效 ID 掩盖不同效果；扩展引用校验至代码生成候选。与 QA03 共用失败不消费规则。

**验收标准：**

- [x] 三张卡均可解析并产生所述效果，作用范围与持续时间符合说明。
- [x] DOT、反应和普通直接伤害按各自描述验证，避免修复后全部错误套用一种效果。
- [x] 故意注入缺失升级时，内容校验失败，运行时也不静默消费奖励。
- [x] 对照卡“危险悬赏”仍可解析 `curse_boss_bounty` 并正确生效。

**证据：** [观测 JSON](E:/codex/game-qa-20261010/probe-03/observations.json) 的 `boss_rewards`。

## QA05 奖励保底未落实到最终三张卡

**影响：** 低血量精英奖励可能没有生存卡，Boss 前祝福可能没有 Boss 相关卡。

**复现步骤：**

1. 法师生命设为 15/75，奖励 RNG 设为 1，内部升级池 RNG 设为 1001。
2. 分别生成 `elite` 与 `boss_blessing` 奖励，检查最终返回三张卡的标签。
3. 扩展到种子 0 至 99，内部升级池种子为对应种子加 1000。

**预期：** 低于 40% 生命的精英奖励至少有一张生存卡；Boss 祝福至少有一张 Boss 标签卡。

**实际：** 固定输入下精英奖励 23/100 次缺生存标签，Boss 奖励 6/100 次缺 Boss 标签；两类种子 1 都可复现。此比例不代表所有构筑的理论概率。

**代码位置与原因：** [run_reward_pool.gd](../../scripts/upgrades/run_reward_pool.gd:34) 在完整候选列表上检查保证，再 `slice` 前三项；保证卡可能落在返回范围之外。

**修复建议：** 保底检查针对最终可见三张卡执行，同时保持卡数、候选合法性和去重。Boss 保底卡的效果需依赖 QA04 修复。

**验收标准：**

- [x] 原 100 组种子下，满足条件的最终奖励均有对应标签。
- [x] 检查生命刚低于、等于和高于 40% 的边界，保底规则与定义一致。
- [x] 最终卡数符合配置，卡片不重复，所有引用有效。
- [x] 候选不足或缺少对应类别时，仍有合法可领取的兜底方案。

**证据：** [观测 JSON](E:/codex/game-qa-20261010/probe-03/observations.json) 的 `reward_guarantees`。

## QA06 临时护盾与实际效果不一致

2. 记录护甲与升级定义，领取卡片。
3. 对照“一次性护盾，抵消下一次高额伤害”的说明。

**预期：** 运行效果与名称、描述、推荐理由相符。

**实际：** 引用 `survival_defense`，护甲从 0 增为 2；定义没有一次性护盾机制。

**代码位置与原因：** [run_reward_pool.gd](../../scripts/upgrades/run_reward_pool.gd:53) 的卡片文案与 [upgrades.json](../../data/upgrades/upgrades.json:355) 的效果不一致。

**修复建议：** 根据产品既定设计选择实现护盾，或将卡片完整改为护甲奖励；名称、标签、描述与推荐理由需要一起核对。

**验收标准：**

- [x] 卡片所有文案与实际效果一致。
- [ ] 若保留一次性护盾：首次符合条件的伤害正确吸收，消耗后第二次不再吸收。
- [x] 若保留护甲：数值增量、持续范围正确，不再描述一次性挡伤。
- [ ] 与现有护盾、护甲叠加时没有重复结算或异常免疫。

**证据：** [观测 JSON](E:/codex/game-qa-20261010/probe-03/observations.json) 的 `shield_reward`。

**修复建议：** 按当前操作设计补齐四向移动绑定；若决定仅支持 WASD，则同步修正所有语言中的操作说明。

**验收标准：**

- [x] 支持的每个方向能在实际战斗驱动正确移动，WASD 回归正常。
- [ ] 对角线、松键停止、暂停及菜单导航无异常。

**证据：** [观测 JSON](E:/codex/game-qa-20261010/probe-03/observations.json) 的 `arrow_controls`；现有自动观测直接检查 InputMap，修复后应补真实移动交互验证。

## QA09 DOT 挑战查询旧伤害来源名称

**影响：** 已满足 DOT 伤害占比的胜利不能完成对应地图挑战。

**复现步骤：**

1. 使用真实 RunStatsTracker 记录 1000 点 `damage_origin=status_dot` 伤害，不记录其他伤害。
2. 将统计作为瘟毒墓园 `toxic_fog_graveyard` 的胜利输入，时间 280 秒，调用生产结算服务。
3. 检查 `clear_with_dot_damage` 条件。

**预期：** DOT 占比 100%，满足至少 35% 的挑战。

**实际：** 挑战判断为 false，统计已记录在 `damage_done_by_origin.status_dot`。

**代码位置与原因：** [run_progression_service.gd](../../scripts/game/run_progression_service.gd:165) 查询旧键 `dot`；[damage_rule_registry.gd](../../scripts/combat/damage_rule_registry.gd:13) 定义实际来源 `status_dot`，生产统计按实际来源记录。

## QA10 提前击败 Boss 的存档记录未到达 Boss

**影响：** 结算摘要的 Boss 到达标志与实际流程矛盾，影响记录可信度。

**验收标准：**
