# 技能系统持续改进分阶段执行方案

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. 本轮仅编写方案。后续由当前会话按阶段串行实施，每阶段完成后停止并汇报；本文件不授权自动启动后续阶段、子代理、提交、推送或合并。

**Goal:** 让每次技能升级产生明确收益，让核心与融合适配完整一局，并建立可重复验证、可独立调参和可回退的维护流程。

**Architecture:** 复用现有技能定义、成长适配器、混沌循环、融合运行时和采样工具。先补齐技能设计契约与测量，再修正成长和循环，随后调整构筑选择，最后完成统计与人工验收。数值读取集中到技能配置与公共解析方法，预览和运行时共用解析结果；玩法提交与纯数值提交分离。

**Tech Stack:** Godot 4.6.3、GDScript、JSON、Node.js、PowerShell。复用现有验证脚本，无新增产品依赖。

**Spec:** 本文件的设计约束、阶段任务与验收标准构成本轮方案；承接 `../specs/2026-10-09-skill-system-rebalance-design.md` 中仍有效的结构约束。上一轮的原始证据见 `../../skills/skill_rebalance_validation.md`。历史规格中的阶段状态不能覆盖当前实现或本轮发布状态。

**状态：** 方案已编写，R1–R6 均未执行。上一轮 M1–M4 代码已合入，统计平衡、完整局流程、人工试玩和部分性能验收仍开放。本轮使用 R1–R6 编号，避免与历史 M1–M4 混淆。

## Review Focus

1. 空目标、失败施法、复制施法与跨神系施法，不应错误消耗蓄能或触发自己的复制循环（R2、R3）。
2. 原技能成长与复制倍率成长同时存在时，各成长仅应用一次；负向参数和控制门槛不得被品质盲目放大（R2、R4）。
3. 同帧解冻、诅咒结算、死亡和转移只能完成一次有效结算或转移，来源移除后无残留（R4）。
4. 零资源、带入资源、Boss 带小怪、多 Boss 目标及暂停恢复，资源节奏有界且可解释（R3）。
5. 满槽、最小构筑、前置不足、品质差异、早死和超时，不产生死升级，也不能被采样器隐去（R1、R5、R6）。

## 一 设计选择与交付边界

推荐采用“先恢复升级价值，再修循环，再验证构筑”的顺序。只调倍率成本低，但会保留无效升级和融合机会成本；整体重做六神系影响面过大，也难以判断改善来自哪里。本方案按问题拆分，阶段间形成可比较版本。

每个技能需要一份可维护的设计记录：战斗职责、状态来源、触发条件、槽位成本、逐级收益、品质作用、Boss 路径及失效边界。实际执行参数保存在 `data/skills/skills.json`，审计记录只保存定位和验收预期，不建立另一套运行时数值表。

新增配置与接口仅在对应阶段需要时引入，禁止为本轮搭建通用技能编辑器或新的事件框架。完整 144 技能审计要做，但不代表同时重做全部技能。

| 阶段 | 交付结果 | 前置 | 阶段边界 |
| --- | --- | --- | --- |
| R1 设计契约与基线 | 技能问题清单、成长表、可复现基线 | 无 | 不修改正式玩法数值 |
| R2 升级收益与描述 | 无效升级得到修正，描述与实际一致 | R1 | 不改变核心蓄能经济 |
| R3 Boss 循环 | 核心及相关强化在单体战可运转 | R2 | 不修改敌人强度补偿结果 |
| R4 融合收益 | 功能型融合升级有效，冰棺有单体收益 | R3 | 不要求全部融合都提高直接 DPS |
| R5 构筑与技能职责 | 槽位投入可理解，有限技能差异化 | R4 | 不扩槽、不改变替换规则 |
| R6 平衡与持续维护 | 多种子、完整局、人工和性能报告 | R5 | 未通过项目保持开放，不虚标发布 |

## 五 R3 Boss 循环

**目的：** 让清群核心在单目标决战中有持续反馈，并控制密集目标导致的资源膨胀。

**主要文件：** 技能与共享配置、`skill_resource_counter.gd`、资源 HUD；扩展 `verify_fire_curse_boss_cycle.gd`，新增 `verify_skill_boss_resource_budget.gd`。

**设计规则：** 普通怪死亡的 +1 保持；精英/Boss 非死亡资源独立配置，沿用现有计数接口 `event_amount(...) -> float`。速率限制按技能实例和战斗秒统一计入，限制的是非死亡路径；暂停不推进窗口，重开/移除清理计数和窗口。

- [ ] 用零资源单 Boss 测试固定旧版首次触发时间，并记录燃烧覆盖和实际诅咒结算间隔。
- [ ] 首轮候选：有效燃烧每次 tick +1 点；有效诅咒每次结算 +3 点；非死亡资源每技能每秒最多 3 点。炼狱与归棺门槛暂保持 20，初始资源为零时理论首次触发约 20～21 秒。用时间戳覆盖持续命中、断档与多目标，并验证事件不能重复入账。
- [ ] 关联检查燃爆连锁、灵魂收割等共用计数路径。共享转换不能无意把低门槛强化变成无限高频；必要时在配置中提供技能独立权重，保留共同去重与限速实现。
- [ ] 比较无小怪、带小怪、带入蓄能和多精英场景。复制及不合格二级输出不能给自己充值；普通死亡链不因本轮转换自动增强。
- [ ] 为雷电、冰霜、神圣、混沌核心记录首次反馈和触发频率，只有被复现的节奏问题进入本阶段修订。
- [ ] HUD 显示当前资源、门槛和触发反馈；文本说明 Boss 非死亡获取规则，不能用“若干次”隐去实际门槛。
- [ ] 运行相关核心、事件链、暂停/移除/重开用例与全量回归。

**退出标准：** 在固定的持续维持状态、无小怪、零资源单 Boss 夹具中，火焰与诅咒核心首次反馈落在 10～25 秒，60 秒可见至少两次有效爆发。多目标获取符合配置上限。该门槛是本轮试验目标，不能通过补血、修改敌人或预充资源绕过。

**汇报：** 首次触发时间、60 秒次数、清群对照、关联强化的收益变化。完成后停止。

## 六 R4 融合收益

**目的：** 修正功能型融合的升级价值，让融合在其目标场景中值得占用唯一槽位。

**主要文件：** 技能配置、融合运行时与动作、成长解析、预览；新增 `verify_fusion_upgrade_value.gd`、`verify_ice_coffin_payoff.gd`，扩展现有融合竞态及来源测试。

**设计规则：** 伤害、控制、传播、生存分别有验收指标。原生融合的半径、功能增益等参数必须经过已声明的成长解析；不能只对 `effects` 内动作成长。固定的事件过滤、递归上限与去重不随等级改变。

- [ ] 为 60 融合逐项核对 Lv1/Lv2、史诗/传奇以及所需前置。仅有资格不等于触发频率足够；记录最小构筑的有效触发数。
- [ ] 功能型融合选择一个清楚的升级维度，并在审计表中绑定真实结果断言。冰棺转移半径首轮候选 336→420，确保只有升级后的边界目标能收到转移。
- [ ] 冰棺保持冻结暂停与死亡转移；补充“存活解冻后下一次有效诅咒结算获得 20% 增伤”，Lv2 候选 30%。该奖励每次结算最多领取一次，不叠加；转移时不携带这一奖励，不把本次结算伤害再次复制为一次结算。同步修改描述与预览。
- [ ] 用无小怪 Boss 配对验证冰棺的补偿是否覆盖暂停成本；未覆盖则在本阶段调整补偿或暂停规则，不能仅因奖励已触发就接受设计。冰冻时长和覆盖率不同，结论必须绑定构筑。
- [ ] 纯功能融合品质只允许增强已声明的正向收益；转移范围或解冻奖励等字段需显式声明。如果没有安全的品质维度，在阶段汇报中提出独立品质规则方案，不能让不同品质只换边框，也不能悄悄改变全局抽取规则。
- [ ] 覆盖冻结到期/死亡/转移同帧、暂停恢复、来源移除、无目标和二级输出；每条有效事件只有一次结算或转移。
- [ ] 每个融合至少一个目标场景与一个边界场景，同预算比较“融合 Lv1”与“已有技能升一级”，再比较融合 Lv1/Lv2；数值结论留给 R6 的扩样确认。

**退出标准：** 所有功能型融合升级与品质差异都有实际结果证据；冰棺在指定 Boss 对照中获得可测的结算收益且不因竞态双结算。无法覆盖的场景明确标识，不宣称所有融合全场景更强。

**汇报：** 融合收益类型、前置频率、升级差异、Boss 净收益与竞态结果。完成后停止。

## 七 R5 构筑选择与技能职责

**目的：** 让玩家理解技能的投入成本，先加强少数职责重叠技能，再决定是否推广。

**主要文件：** 技能配置、选卡预览与弹窗、现有区域动作实现；新增 `verify_skill_role_choices.gd`、`verify_skill_slot_tradeoffs.gd`，扩展资格与供给测试。

- [ ] 建立 2/3/5 普通槽的最小构筑夹具，比较“一个强化槽”与“一个额外直接输出槽”，同时记录输出、状态覆盖、生存和触发频率。普通槽预算相同，核心/融合资格相同，不给实验组多一个槽。
- [ ] 在卡片增加主要职责与实际前置进度，明确状态来源、尚缺组件和槽位占用。复用 RequirementPolicy，UI 不能自行发明准入规则。复杂说明进入详情，主卡仅保留最重要的职责、收益和条件。
- [ ] 第一批职责差异调整限于冰霜领域、暴雪云团和神圣结界：冰霜领域突出定点冻结准备与到期区域，暴雪云团突出追踪覆盖，神圣结界突出入圈保护与驻留收益。先通过同几何/同预算对照确认已有差异是否足够，只有不足时再修改机制。
- [ ] 若需修改，首轮每技能只改变一个职责维度，分别在审计表冻结范围/持续/叠层或入圈收益候选值；不在同一提交同时增加伤害和覆盖。明确验证“移动目标”和“需要离圈避险”的场景。
- [ ] 其余神系本阶段输出职责矩阵与重叠清单，不同时重做六神系。抽卡规则、替换次数、品质抽取与槽位上限保持当前规则。
- [ ] 跑满槽、前置不足、最小构筑、升级卡、核心和融合供给及 UI 实际选择回归。

**退出标准：** 卡片条件与真实准入一致；三项首批技能能用场景解释自己的优势与成本。玩家不会被提示选取不存在的功能或无法兑现的升级。

**汇报：** 槽位对照、职责矩阵、具体机制变化与真实选卡画面。完成后停止。

## 八 R6 平衡验收与持续维护

**目的：** 关闭上一轮验收缺口，并形成后续每次新增/调参都能复用的流程。

**主要文件：** 矩阵预设与采样器、性能工具、回归套件、审计与验证报告；新增 `docs/skills/skill_sustainability_release.json`。

- [ ] 冻结版本、配置哈希、预算、角色、品质、种子、控制器和采样视口。补充原生融合触发与收益计量；来源存在时间不能直接当作玩家有效增益覆盖。
- [ ] 完成六神系各三构筑、六场景的每构筑 10 探索种子，再用 20 个未参与调参的新种子确认。沿用预设中的探索与确认种子集，禁止看确认结果后继续调参并仍称其为独立确认。
- [ ] 15 神系组合每组合至少 5 个配对种子；R4 改动过的具体融合全部加入配对，不以神系组合抽样替代全部 60 技能行为验收。异常组合扩至 20 个新种子。
- [ ] 报告清除率、早死率、清除时间分布、实际伤害、溢出、核心首次反馈、融合触发、有效增益、生存与护盾吸收。死亡和超时保留为失败终态；幸存者时间统计单独注明。
- [ ] 纯数值调参分小批进行：单提交单问题、每轮每字段优先控制在 10% 内，并记录假设、旧值、新值和配对结果。功能成长或资源合同修复不伪装成 10% 内数值微调；无改善就回退该批。
- [ ] 完整局验证分两类：用固定夹具完整运行 300 秒确认终局流程；自然抽卡无补血/额外授予的每神系两局记录实际结局。死亡自然局不能算完整流程通过，固定夹具也不能当自然成型证明。
- [ ] 人工试玩六神系各两局，记录选卡理解、成型过程、Boss 反馈、融合收益及失败原因。人工结果须由实际试玩提供，脚本运行不能代签。
- [ ] 渲染性能在同机、同视口、同配置下串行采样，暖机后测真实 process_frame 墙钟间隔，覆盖固定 24 怪/12 技能和局末密集场景。保留绝对 p95 ≤16.7ms 与相对基线退化 ≤10% 两项；任一未达标保持开放，不能以一项抵消另一项。相对比较使用同协议可复验基线。
- [ ] 完成真正不可移动 Boss、长时间对象回收/事件队列，以及仅回退纯数值提交的演练。混合玩法/数值提交整块回退不能代替精细调参回退。
- [ ] 跑最终全量回归，生成发布记录，分别记录功能、平衡、性能、人工与回退结果。只有实际验收全部完成才能将 `release_status` 改为 `accepted`；否则维持 `acceptance_open` 并列明开放项。

**平衡目标使用方式：** 上轮单体跨度 ≤1.5、清群跨度 ≤1.8 和融合 15%–35% 是未验收目标，本轮可以作为诊断参考。必须按技能职责和有效预算分组；辅助、控制或生存融合用自己的指标验收，不强迫全部满足统一 DPS 增幅。若需更改发布门槛，在扩样前记录原因与新门槛，不能采样后降低标准以获得通过。

**退出标准：** 上述记录与原始证据齐备；阶段功能正确且目标场景收益被确认；人工、性能、回退等未完成项不会被标为完成。未通过时汇报可交付的测试版本及剩余范围，继续本阶段整改须依据用户后续指令。

**汇报：** 新旧对照、完整回归、自然与固定流程、人工结果、性能、回退及发布状态。完成后停止。

## 九 每阶段汇报与长期维护

每阶段使用同一份简短报告：

1. 本阶段目标与已完成范围。
2. 具体技能/规则变化及原因，包含原值与新值。
3. 验证命令、版本、结果和原始证据目录。
4. 已通过、未通过、未验证分别列明。
5. 未解决风险与下一阶段前置；停在当前阶段，不自动续做。

每次后续新增技能、升级里程碑或融合，必须同时更新设计审计、逐级/品质结果用例和预览；涉及复制、资源或冻结时，加入相应边界用例。改变核心循环必须重跑单 Boss 与带小怪夹具；改变覆盖/持续/输出必须重跑对应职责的等预算采样。

日常修订只跑变更相关功能与边界；阶段交付跑全量回归；正式平衡版本跑确认种子、人工与性能检查。出现新失败或新机制才扩大测试范围，不反复重跑无关检查。

调参提交只包含数值及相应报告，机制提交单独保存。每个候选版本记录代码版本、配置哈希、采样协议和未解决项。基线更新只发生在验收后的版本，失败候选不能覆盖基线；所有旧证据保留，避免后续把“当前通过”错误理解为“历史问题已全部解决”。

**实施顺序：** R1 → 阶段汇报 → R2 → 阶段汇报 → R3 → 阶段汇报 → R4 → 阶段汇报 → R5 → 阶段汇报 → R6 → 最终验收报告。
