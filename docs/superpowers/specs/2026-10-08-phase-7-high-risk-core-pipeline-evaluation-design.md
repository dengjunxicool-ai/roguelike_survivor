# 阶段 7：高风险核心链路评估设计

## 状态

本规格记录已经批准的阶段 7 架构与详细设计。阶段 7 的目标是用契约测试和现有验证重新评估高风险核心链路，而不是默认重构这些链路。

当前步骤只授权形成书面设计供用户审阅，不授权提交代码。后续新增验证脚本、登记验证入口或修改工程文档，必须先形成实施计划并由用户批准。任何生产代码修改都需要在测试暴露真实缺陷后另立小批次、单独说明证据并重新获得批准。

阶段编号必须继续使用既定路线图中的“阶段 7”，不得衍生“7A”“7B”“阶段 8”等新编号误导项目进度。

## 目标

阶段 7 评估以下高风险链路：

1. `DamageApplicationService` 与伤害应用流水线；
2. 状态结算、DOT tick 与元素反应；
3. 怪物死亡、奖励和击杀事件流水线；
4. 敌人生成、波次和 Boss 时间线；
5. 玩家死亡或 Boss 击败后的结算、进度记录与存档。

阶段完成时必须能回答：

- 这些链路的现有行为是否有可重复的自动化证据；
- 是否存在已证实的缺陷、性能瓶颈或契约缺口；
- 哪些链路应保持冻结；
- 如果存在真实问题，最小修复边界是什么。

## 已确认现状

### 伤害应用

`DamageApplicationService` 是薄门面，玩家和敌人的应用顺序由 `DamageApplicationPipeline` 及独立 application stages 负责。现有伤害公式、typed packet、玩家受击和敌人受击测试已经覆盖大量分支。

结论：复用现有验证，不因兼容入口或文件结构继续重构。

### 状态与元素反应

`StatusEffectManager` 同时协调状态应用、叠层、tick、反应队列、事件、查询和视觉刷新。它已有 `StatusTickScheduler`、`StatusEffectQuery`、`StatusEffectTickHelper` 和 profiler 等协作者，但仍是本阶段复杂度最高的运行时组件。

结论：复杂度本身不是重构授权。先复跑状态契约并用跨链路测试确认 DOT、反应、伤害与死亡衔接；没有失败时保持冻结。

### 怪物死亡与奖励

`EnemyBase` 通过 `EnemyDeathPipeline` 执行死亡策略，通过 `EnemyRewardController` 处理魂石、击杀事件、协同通知和统计。死亡 pipeline 已使用 `_is_dead` 防止重复执行，并允许 `self_explosion` 与 `reward_policy` 调整副作用。

结论：新增针对幂等性、顺序和策略分支的运行时契约，不改生产实现。

### 敌人生成时间线

`EnemySpawner` 仍是聚合根，但波次、Boss、生成服务、清理和奖励事件已经委托给独立协作者。现有验证覆盖可见区域批量生成、配置合法性、敌人更新热点和部分 Boss/波次行为。

结论：复跑现有门禁。只有出现可重复的时间线错误或测量确认的性能回归，才另立修复批次。

### 结算与存档

玩家 `died` 信号进入失败结算，Boss `boss_defeated` 信号进入胜利结算。`UIManager` 构建 `RunResultState`，`RunProgressionService` 记录最后一局摘要、全局计数、角色专精、地图挑战和固定挑战，`SaveManager` 写入 `user://save.cfg`。

当前结果页面、解锁缓存和诊断入口有局部验证，但缺少“终局信号到持久化结果”的完整自动化契约。

结论：这是阶段 7 首要且有证据的测试覆盖缺口。

## 方案比较

### 方案 1：契约优先，失败后再修复（采用）

新增少量 dev-only 运行时契约，复用现有伤害、状态、生成和结果页面验证。测试通过时明确冻结生产链路；测试失败时先分类，再为真实缺陷单独设计最小修复。

收益：变更范围小、定位明确、可独立回滚，不会把评估变成无证据重写。

风险：不能替代所有人工游玩场景，但适合作为稳定门禁。

### 方案 2：完整自动游玩验收（不作为首批）

从开局运行到失败或胜利，验证真实场景的最终结果。

收益：接近玩家实际路径。

风险：耗时长、随机性高、失败定位困难，并且已有 full-run 工具不适合作为每次小批次的唯一门禁。可作为最终补充证据，不能取代确定性契约。

### 方案 3：直接拆分核心大类（拒绝）

立即拆分 `StatusEffectManager`、`EnemyBase` 或 `EnemySpawner`。

拒绝原因：当前没有缺陷、性能数据或扩展需求证明此类改动的收益足以覆盖风险。

### 明确排除

- 修改状态叠层、持续时间、tick、反应限制或视觉效果；
- 修改怪物死亡顺序、奖励数值、掉落概率或经验；
- 修改波次时间、敌人数、Boss 行为或生成算法；
- 修改存档 schema、正式存档位置或结算 UI；
- 因文件长度、方法数量或 `Dictionary` 使用而拆分类；
- 性能优化、玩法调整和美术调整。

## 验证设计

### 1. 现有核心门禁

阶段 7 必须复跑并记录与下列领域匹配的现有验证：

- 伤害公式、typed damage packet 和 numeric damage 禁止检查；
- 燃烧、火焰、冰冻易伤、状态 scheduler 与 tick 间隔；
- 敌人生成配置、可见区域批量生成和敌人更新热点；
- 结果页面诊断、解锁缓存和 Godot headless 启动；
- UTF-8 文本编码和 `git diff --check`。

现有门禁失败时先判断原有失败、环境问题或本次测试回归，不得通过放宽断言、跳过测试或修改玩法规则取得绿色结果。

### 2. 怪物死亡与奖励运行时契约

新增确定性测试，构造最小敌人和奖励协作者，验证：

1. 第一次死亡按既有顺序执行奖励、击杀通知、`died` 信号、死亡效果和经验掉落；
2. `_is_dead` 在副作用前置为 `true`；
3. 第二次执行不重复发放魂石、经验或击杀事件；
4. `self_explosion` 保持现有默认抑制项；
5. `reward_policy` 只覆盖指定策略键，未指定行为保持默认；
6. 正常伤害入口仍通过 `take_damage()` 与 `DamageApplicationService` 进入死亡链。

测试不依赖正式敌人数值、资源或 UI。

### 3. 终局结算与持久化运行时契约

新增确定性测试，覆盖失败和胜利两条路径：

```text
玩家 died ──> RESULT_DEFEAT
Boss defeated ──> RESULT_VICTORY
        └──> RunResultStateBuilder
             └──> RunProgressionService
                  └──> SaveManager
                       └──> ResultScreenController
```

必须验证：

1. 玩家死亡只能进入失败结算，Boss 击败只能进入胜利结算；
2. 已处于任一结果状态时，后续终局信号不能覆盖结果；
3. 同一局 `_record_result_progression_once()` 只记录一次；
4. `last_run_summary` 的状态、角色、地图、时长、击杀和魂石字段正确；
5. 总局数、胜利、失败、Boss 击杀和地图计数只增加一次；
6. `SaveManager.get_last_run_summary()` 返回深拷贝；
7. 调试局玩家死亡继续不进入正式失败结算；
8. 重复刷新结果页面不能重复写入进度。

### 4. 存档隔离

所有会写 `user://` 的阶段 7 验证必须：

- 使用位于 `E:\codex\godot-phase7` 下的独立 `APPDATA` 和 `LOCALAPPDATA`；
- 不读取、复制或覆盖玩家正式 `save.cfg`；
- 为每次验证使用可清理的专用测试目录；
- 不向 C 盘写入缓存、报告或临时文件；
- 报告测试前后的隔离路径和清理结果，但不得输出敏感凭据。

Godot 运行逻辑验证继续直接调用已批准的 Godot 可执行文件，不通过 npm 间接启动 Godot。`package.json` 中可以登记验证入口，但沙箱内的正式执行必须遵守项目现有原生崩溃规避说明。

## 数据流与职责

阶段 7 不建立新的生产服务。新增验证代码只负责：

- 搭建最小依赖；
- 触发公开入口或现有信号；
- 观察副作用、顺序和持久化结果；
- 清理测试数据；
- 以非零退出码报告失败。

验证不得在测试中重新实现生产规则，也不得直接改写内部状态来伪造通过。只有为了隔离外部资源而使用最小替身；替身必须记录调用，不复制业务逻辑。

## 错误分类与停止条件

测试失败后按以下顺序处理：

1. 测试环境或存档隔离错误；
2. 测试替身与真实接口不一致；
3. 合入前已经存在的基线失败；
4. 阶段 7 新测试暴露的生产缺陷。

前三类在测试范围内修正并复跑。第四类必须停止扩大范围，提交证据表，并为该缺陷单独形成设计和计划。未经批准不得修改生产链路。

如果新增契约和现有门禁全部通过，阶段 7 的默认结论是：

- 五条核心链路保持冻结；
- 不实施架构重构；
- 把测试作为长期回归门禁；
- 未来只有明确缺陷、性能数据或扩展需求才能重新开启对应链路。

## 回滚

阶段 7 测试批次必须能够独立回滚：

1. 删除新增验证脚本；
2. 删除对应 `package.json` 入口；
3. 恢复阶段 7 工程文档记录；
4. 删除 `E:\codex\godot-phase7` 下本批次创建的精确测试目录；
5. 重新运行阶段 6 总体验收和原有核心门禁。

回滚测试不得撤销阶段 6 数据入口收口、用户已有修改或其他无关提交。
